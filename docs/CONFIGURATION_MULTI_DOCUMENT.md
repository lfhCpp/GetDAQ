# 多文档配置工作区与 Save All

本功能让多个本地配置根文件共同编辑、共同审阅，再保存全部改动。它使用 MUSIC 熟悉的 `.h/.cpp/.ui` 窗口结构，编辑和校验只在操作电脑执行，不调用 ECC、板卡或数据接收器。

旧 ConfigWidgets 的 `Workspace::saveAll()` 遍历模型，逐个保存 Undo 栈尚未 clean 的模型。因此“保存全部”不等于跨文件原子事务。本实现先准备所有临时文件，再写持久恢复记录、逐个原子替换；磁盘错误或进程中断仍可能留下部分新文件，需要核对。新版配置工具还使用[共享读、独占写协议](CONFIGURATION_SOURCE_TRANSACTIONS.md)，避免合作读取者在保存期间加载混合版本；它不能强制旧软件或外部编辑器遵守。

## 1. 从哪里打开

1. 在主窗口未连接、未采集时，打开 `GET configuration files...`。
2. 点击 `Multi-document workspace / Save All...`。
3. 点击 `Add root configuration...`，选择第一个 `.xcfg` 或 `.xml`。
4. 再添加其他根配置。窗口上方列出所有已打开的根文件；标签页显示根文件及其本地 include 来源。

连接/活动状态进入配置界面时，该窗口只能查看来源，不能编辑、审阅保存或调用 Save All。打开来源不会连接硬件。旧的声明树编辑界面仍按原行为即时保存；新工作区的文本编辑先留在内存。两者不要同时编辑同一批来源，外部改动会使新工作区拒绝覆盖。

同一个规范路径的共享 include 只有一个标签页；修改这个标签会影响所有使用它的已打开根配置，不会生成几个互相冲突的副本。鼠标停在标签上可看完整路径，避免把不同目录的同名文件认错。

## 2. 编辑、审阅、保存的顺序

1. 在对应文件标签中编辑 XML。未点击 Save All 前，文件字节不会因为文本编辑写入磁盘。
2. 点击 `Review all pending sources`。窗口一次接收所有标签的文本，解析全部根文档、include、继承、类型和范围。
3. 审阅下方 JSON：`files_to_replace` 列出将被替换的文件；`root_reviews` 分别列出每个根配置的有效变化及来源摘要变化。
4. 确认各根配置的影响后，点击 `Save All reviewed changes`。
5. 成功消息列出保存文件数量。后续新的修改需要重新审阅。

只打开文件、不编辑，或者文本恢复到原值，不会把文件当成需要替换的来源。未编辑的 CRLF 文件保留原字节；实际文本编辑由编辑器生成新 UTF-8 文本，换行可能统一为 LF。原始注释、CDATA、属性和未知字段都作为完整源文本保留，除非使用者明确编辑了它们。

这个入口是源文本编辑，不自动插入 XML 标签或生成所有旧命令。声明树的已有结构编辑和覆盖仍在原编辑窗口使用。多文档工作区现在有统一的“已审阅来源组”历史：每次成功审阅的实际文本变化作为一组，能够同时撤销或重做多个文件。

### 2.1 标签内撤销与整组撤销有什么区别

编辑某个标签时，编辑器自己的撤销只影响该标签的输入，例如撤销刚输入的一行。窗口上的 `Undo reviewed source group` 和 `Redo reviewed source group` 则操作一次成功审阅所记录的整组文件变化。

例如，根配置把数值从 2 改为 12，同时共享模板把合法范围从 `[0,9]` 改为 `[0,20]`。只撤销范围会使数值 12 非法；整组撤销会一起恢复数值 2 和范围 `[0,9]`，不会留下半个修改。

操作顺序如下：

1. 修改相关标签，点击 `Review all pending sources`。校验失败时不增加历史，也不修改已暂存的合法组合。
2. 成功审阅后，点击 `Undo reviewed source group`。所有相关标签同时恢复上一组的字节；磁盘文件不变。
3. 如果需要返回，点击 `Redo reviewed source group`。所有相关标签同时恢复下一组；磁盘文件仍不变。
4. 撤销或重做都会使旧的保存审阅失效。重新点击 `Review all pending sources`，检查每个根的影响，再点击 Save All。

还有未审阅的标签文字时，整组撤销/重做按钮禁用，以免直接丢掉正在输入的内容。可以先使用本标签的文本撤销，或者把合法修改审阅为下一组。单次敲键只更新当前标签的待审阅状态，不扫描全部来源标签。

重复审阅相同字节不会产生一条新历史，也不会丢掉仍可重做的分支。撤销后提交一组新的合法修改，才会替换原来的重做分支；失败的修改不替换分支。

### 2.2 保存后按 Undo 会不会立刻改回磁盘

不会。历史保留准确的修改前后字节，Save All 成功后仍可撤销，但撤销的结果首先成为一组新的内存待保存内容。

例如，已经把 12 保存到文件，再按整组 Undo，标签显示 2，而磁盘仍是 12。只有重新审阅并执行 Save All，磁盘才会变为 2。关闭窗口时丢弃内存修改，也不会把磁盘上的 12 自动恢复为 2。

这不提供磁盘事务回滚，更不是撤销硬件配置。配置窗口不能用来撤销一次已经发给板卡的命令。

### 2.3 历史的校验和容量

- 每次 Undo/Redo 都重新核对已知来源的磁盘字节，并校验组合结果对所有当前打开的根是否合法。来源被其他软件修改时拒绝；添加一个新根后，旧历史若使新根非法，也会拒绝，保持当前内容和历史位置。
- 添加根文件不属于文本历史，Undo 不会关闭该根。需要恢复一个旧组合时，应先确定该组合对所有当前根都有效；不能绕过范围或 include 校验。
- 最多保留 32 组历史；历史中的修改前后字节按保守方式计数，合计上限 128 MiB。超过组数或字节预算时，淘汰最早的整组记录；不能继续撤销到已淘汰的状态。共享字节也按每条记录计数，不用内存隐式共享来放宽预算。
- 字节预算不包括所有 Qt 树、编辑器文本和容器开销，不是整个进程 RSS 上限。源文件集合仍受第 4 节的 64 MiB 预算约束。
- 历史仅存在于本次工作区进程中，不自动写日志；关闭或重新打开窗口不恢复历史。Save All 部分失败后冻结历史和编辑，先检查磁盘并重新打开。

## 3. 为什么要一次审阅所有标签

例如配置 A 中的阈值从 8 改成 12，而共享 include 中的范围从 `[0,9]` 改成 `[0,20]`。只改值时配置无效；只改范围后再改值会形成一个临时中间版本。

工作区可以先在两个标签中编辑，然后统一审阅最终组合。组合无效时，不保留“前几个标签成功、后几个失败”的部分暂存，也不写盘。有效时，对每个已打开根配置展示前后变化，再允许 Save All。

只审阅本工作区打开的根配置，不能发现其他未打开工程是否引用相同 include。保存共享文件前，应把相关根文件加入工作区，或使用 [隔离工作区副本](CONFIGURATION_WORKSPACE_COPY.md) 在独立目录编辑。

## 4. 检查和拒绝规则

| 情况 | 行为 |
| --- | --- |
| XML、UTF-8、类型或范围无效 | 审阅失败；不写盘，不替换此前暂存 |
| include 环、文件不存在或资源超限 | 解析失败；修正源文本后重新审阅 |
| 多根使用同一来源 | 共用一份内存内容，所有根一起核对 |
| 改动 include 后留下不再使用的脏来源 | 仍检查该来源本身有效；它仍列在待保存文件中，不因脱离根树而悄悄丢弃修改 |
| 审阅后又改一个字符 | 撤回 Save All 按钮，重新审阅 |
| 外部程序修改、移走或替换来源路径 | 拒绝覆盖；核对后重新打开，不自动合并 |
| 同时添加新根而有未审阅文本 | 拒绝添加，先审阅当前文本 |
| 已有部分保存或最终来源核对失败 | 列出结果，冻结继续编辑/自动重试，必须检查并重新打开 |

限制是最多 16 个根配置、256 个已知来源；单来源最多 8 MiB，来源字节集合最多 64 MiB。解析器仍有每根 include 深度 32、XML 深度 128 和节点 100000 的限制。这些是输入和结构预算，不是整个 Qt 进程 RSS 的上限；暂存、预览和树模型也占内存。

新增 include 必须引用已经存在的本地文件；不支持以待创建文件作为 include，也不加载数据库、HTTP 或其他网络资源。来源使用规范路径去重，不宣称识别不同路径的硬链接别名。

## 5. Save All 的磁盘过程与失败处理

保存函数先重新计算当前审阅，核对它与用户看到的版本、字节和报告完全相同，再核对所有已知来源仍等于打开时的磁盘字节。然后为每个待保存文件创建 `QSaveFile` 临时文件，关闭 direct-write fallback；如果有任一临时文件不能准备，前面的来源也不会被替换。

所有临时文件准备好后，再按路径顺序逐个 commit。每次替换前重新核对来源；已成功替换的文件更新工作区基线，未成功的文件保留暂存。失败报告分别列出 `Saved` 和 `Remaining`，不会把“保存部分成功”显示为“全部成功”。

若已有文件替换后失败，或者最终核对发现来源漂移，窗口停止继续保存。请按以下步骤处理：

1. 保留报错中的已保存/未保存路径清单，先不要启动现场采集。
2. 在文件系统检查这些来源，并与原备份和审阅结果比较。
3. 未保存文本仍在只读标签中，可以复制到另一个安全的新文件；不要盲目覆盖原文件。
4. 关闭工作区并重新打开经过核对的一致配置。重新打开会重新读取磁盘，不会重放上一次 Save All。

关闭窗口时，如果仍有未保存文本或暂存，会询问是否丢弃内存修改；取消可以继续编辑。丢弃不会恢复已经写入的文件。

逐文件原子替换不能保证全部文件在一个瞬间一起更新。第11节的持久恢复记录可以在明确核对后完成候选或恢复原始来源；[来源事务协议](CONFIGURATION_SOURCE_TRANSACTIONS.md)协调同用户、同操作环境和同缓存域的新版读写者。它不提供自动回滚、任意外部程序的强制互斥、真实断电验收或恶意目录替换防护。外部编辑器仍可能在检查与替换之间改动来源；应在独占的离线配置工作目录使用，不作为运行中硬件配置热更新机制。

## 6. 代码结构和验收范围

- `common/config/xcfgworkspace.h/.cpp`：多根来源与暂存、准确字节的整组历史、全根校验、审阅版本绑定和 Save All 结果。只使用 Qt Core 与已有便携配置核心，不增加第三方依赖。
- `apps/envoy/configurationworkspacewindow.h/.cpp/.ui`：来源标签、根清单、审阅和保存按钮；连接模式只读。
- `XcfgDocument`：保留源字节与 include 路径；工作区通过受限内部入口构造内存候选，不把候选字节伪装成磁盘加载状态。
- 原生接收器、写盘队列和事件导出未改；Save All 结果不是板端加载或当前全量寄存器凭据。

初始 Save All 验证见[第70.18节](VALIDATION.md#7018-多文档配置工作区与-save-all2026-10-12)，新增整组历史的最终证据见[验收记录](VALIDATION.md)。完整跨文件事务、跨文件结构迁移、与原声明树命令统一的历史、更广泛旧库接口和实际硬件加载仍须继续完成。旧工作区包只有 Save All，使用整组历史须确认采用本轮的新程序，不能用旧包的通过结果替代当前构建。

## 8. 声明树结构编辑与文本共用工作区历史

工作区现在提供 **Edit workspace structure...** 按钮。它与文本标签使用同一份内存来源、同一组历史和同一个 Save All；不会另外打开一个直接写磁盘的单文件编辑器。

### 8.1 实际操作顺序

1. 在多文档工作区加入需要共同核对的全部根文件。共享include仍只有一份物理来源。
2. 若标签中已有未审阅的文本，先点击 **Review all pending sources**。未通过的文本不能与结构编辑混合；结构按钮保持禁用。审阅通过以后，结构编辑使用的是暂存后的文本，即使尚未Save All。
3. 点击 **Edit workspace structure...**，选择已打开根，再选择来源声明。下方显示实际来源文件和声明路径，避免把继承投影当成另一个独立文件。
4. 选择操作并填写启用的字段；不同操作只启用相关字段。包括新增对象/标量、删除、改ID/名称、复制、同父排序、标量属性、有效子树物化、本地include/导入及继承对象浅层覆盖。
5. 点击 **Preview all roots**。查看当前源、候选源，以及完整JSON审阅中的 `all_root_reviews`。共享文件的改动必须对每个打开根都合法，不能只看当前所选根。
6. 检查后点击 **Stage reviewed structure**。这只接受到内存并加入一条工作区历史，回到主窗口后标签同步显示候选内容。
7. 主窗口再次点击 **Review all pending sources**，检查累计的文本和结构变化，然后 **Save All reviewed changes**。这是唯一的工作区写盘入口。

取消结构窗口不会接受候选或写盘。修改结构字段会撤回之前的预览；接受时还会重算请求、准确来源字节、全部根审阅、依赖和工作区代次，过期或被修改的候选拒绝。

### 8.2 文本和结构怎样一起撤销

例如首先把共享阈值从2改为3并审阅，然后在结构窗口把该声明改名为 `threshold` 并暂存。这形成两条顺序历史：

- 第一次整组Undo撤销改名，保留值3。
- 第二次整组Undo撤销文本修改，恢复原名称和值2。
- 两次Redo依原顺序恢复值3及改名。

Undo/Redo依然只改内存，不自动覆盖磁盘。保存后也如此；每次都需重新审阅才能Save All。结构历史与文本历史共享原来的32组/128MiB预算，不另设一个无界栈。

结构操作通常改一个物理来源，但其有效影响可能跨多个根。每条历史恢复准确源字节，并重新验证所有当前根；不能为了让撤销通过而忽略后加入根的范围约束。

### 8.3 include和导入使用哪一版内容

结构预览使用已审阅的工作区内存来源。若导入文件已经是工作区已知来源，并在标签中暂存修改，导入读取暂存后的版本；不会悄悄读取磁盘旧版本。修改/添加include也会优先使用该工作区已知来源的暂存内容。

不在工作区的本地输入仍从磁盘读取，并在接受预览前核对其原字节。导入会把内容固定进目标源；接受前外部文件改变会拒绝，接受后已经导入的内容不会自动跟随外部文件更新。

此窗口另有第10节的跨文件声明移动，不创建新include文件；本地路径、已有文件、语义、深度和字节预算保持。所有操作只影响配置文件，不发送硬件命令。

### 8.4 与原单文件编辑器的关系

原 **ConfigWindow** 继续保留它自己的单文件审阅/历史/保存行为。工作区结构窗口复用同一个结构算法，通过私有内存预览入口处理暂存来源；工作区另负责检查所有磁盘基线和组合语义。没有放宽原单文件保存前的磁盘漂移检查，也没有提供可被普通调用方用来跳过检查的公开开关。

两个独立窗口不会共享一个全局撤销栈。不要同时通过另一个窗口保存相同来源；工作区会将外部变化视为漂移并拒绝覆盖。统一的范围是本工作区内的文本及结构编辑，不是硬件回滚或整个应用所有窗口的全局事务。

## 9. 内部结构与校验原理

`XcfgWorkspace::Document` 用规范路径和当前暂存覆盖重建根文档，仍检查实际磁盘基线。`PreviewStructure` 调用已有十四种结构算法生成候选来源，再用工作区组合校验所有打开根，输出准确前后源字节、选定结构变化和全部根报告；此阶段不写盘，也不追加历史。

`StageStructure` 先核对工作区代次，再重算预览并逐项比较来源、候选、快照、依赖和所有根报告，最后使用普通 `StageSources` 接受改动。因此文本和结构自然进入同一条历史路径；保存后的撤销、Redo分支、容量淘汰和部分保存冻结继续共用既有逻辑。

`WorkspaceStructureWindow.h/.cpp/.ui` 负责字段、候选展示和接受；父窗口在接受后同步标签并撤回旧Save All审阅。窗口为模态，避免父窗口在选择声明期间更改来源。接板/活动模式只读，未审阅文本和部分保存冻结状态禁用结构入口。

该实现未增加第三方依赖，使用原有QtCore/Widgets和本地配置算法；它不进入DAQ原始数据通道。已打开本地文件间的现有声明移动由第10节接续；持久化保存恢复由第11节接续；外部可见的跨文件原子事务、全局历史以及硬件UNKNOWN恢复仍未完成。

## 10. 跨文件移动现有声明

### 10.1 什么情况下用它

需要将一个已有对象或标量从来源A移到来源B时，选择结构窗口的 **Move declaration to another source file**。它是真正的“双文件变化”：从原来源删除选定声明，在目标对象的子项末尾插入相同声明；不是只做一份导出副本。

必须先将相关根文件加入同一个工作区，并审阅所有待修改文本。源声明与目标对象最终属于不同的规范来源路径；可以选择两个根，也可以通过同一根里的不同include来源选择实际文件。软件不能确认未打开工程是否还引用这些文件，保存共享来源前要加入所有相关根或先创建隔离工作区副本。

### 10.2 操作步骤

1. 在工作区加入源、目标及共同引用它们的根，审阅已有文本。
2. 打开 **Edit workspace structure...**，选择源根和要移动的来源声明。
3. 选择 **Move declaration to another source file**。
4. 选择 **Move destination root**，再选择 **Move destination object**。目标列表只有对象；将声明插入该对象末尾，不自动改名或改ID。
5. 点击 **Preview all roots**。当前源/候选源标签会同时显示两份文件，完整记录列出源声明、目标对象、include路径改写及每个已打开根的前后影响。
6. 检查全部影响后点击 **Stage reviewed structure**。工作区两个来源标签同步变化；此时磁盘未改。
7. 可以一次整组Undo同时恢复两个来源，Redo再同时暂存移动。若要写盘，重新审阅工作区，再Save All。

取消不会移动。修改任一选择会撤回预览；工作区代次或磁盘来源变化后，旧预览不能接受，先重新核对。

### 10.3 相对include路径如何处理

例如原声明在 `/cfg/source/main.xcfg` 中写 `include="sub/range.xcfg"`。把声明移到 `/cfg/target/main.xcfg` 后，仍写同一个相对字符串会错误地寻找 `/cfg/target/sub/range.xcfg`。

软件根据原文档已经绑定的依赖文件，改写为目标目录下的相对路径，例如 `../source/sub/range.xcfg`，保持指向原依赖。嵌套在移动片段里的每个literal include都单独处理，XML特殊字符按属性语法转义；不同Windows盘符等情况下Qt可能生成绝对路径。依赖文件本身不复制、不移动、不修改，其中的相对引用仍按该依赖自己的位置解释。

完整审阅的 `include_rewrites` 列出原声明路径、原字符串、改写后字符串及 `same_dependency_file`。操作使用已经审阅的内存来源；若依赖文件也有暂存修改，候选仍使用该版，而不是磁盘旧版。

移动片段内部的注释、属性及标量字符引用保留；紧邻片段但在其元素范围之外的注释不自动跟随移动。插入处增加换行，不承诺排版、行号或字符偏移与原位置相同。Undo保留精确原来源字节。

### 10.4 哪些情况拒绝

| 情况 | 结果 |
| --- | --- |
| 移动一个文档根或include文件根 | 拒绝，不能破坏根文件结构 |
| 目标是标量 | 拒绝，标量不能容纳子声明 |
| 源和目标是同一个规范来源路径 | 拒绝，本入口只用于跨文件；同父排序用原Move before/after |
| 目标已有同名称/ID的本地或include声明 | 拒绝，不自动覆盖、合并或换ID |
| 移动后产生include环、类型/范围冲突或其他根无效 | 整组拒绝，源和目标暂存都保持原样 |
| 源、目标、依赖或工作区在预览后变化 | 拒绝旧审阅，重新选择和预览 |
| 候选字节或报告被改变 | 接受时重算并拒绝，不将被改候选当原审阅 |
| 只读/未审阅文本/部分保存冻结 | 工作区禁用结构入口 |

移动可能改变父层继承、共享单位/范围和有效路径。软件不会宣称“换文件后全部语义不变”：它核对组合是否合法，并列出每个当前根的实际差异，由使用者审阅其是否符合目的。保留include依赖只保证引用仍指向同一文件，不代表新父级上下文与旧上下文相同。

### 10.5 Save All部分失败的核对

移动的两个来源以一组内存变化验证和撤销；磁盘Save All先准备所有临时文件并保存第11节的原始/候选恢复记录，再逐文件替换。因此保存过程失败或强制退出时，磁盘仍可能处于移动前后的混合版本，不能仅凭某一个文件已保存就认为移动完成。新版合作读取者会拒绝活动保存或未完成来源记录，外部不合作程序仍可能看到混合版本。

保存前备份涉及的配置来源和include树。发生部分失败时，窗口列出已保存及剩余文件并冻结自动重试；先保留窗口里的准确候选内容，核对磁盘两边的声明及依赖，再按备份或候选进行人工恢复。不要立即关闭窗口丢弃唯一的暂存记录；也不要把内存Undo当作已经写回磁盘。

只有Save All完成且重新解析/审阅的结果与目标组合一致，才算本次声明跨文件移动保存完成。持久化保存意图与人工恢复由第11节接续；[原文件重命名/路径迁移](CONFIGURATION_PATH_MIGRATION.md)由独立入口处理，不能混同。真实断电验收、任意外部读者可见的跨文件原子事务和全应用共享历史仍未完成。

### 10.6 内部实现

`PreviewMove` 绑定工作区代次、源/目标根与声明索引，取得当前暂存的两份来源。它提取源元素范围，对其中的include按原绑定依赖逆序改写，分别生成删除后的源和插入后的目标。候选通过已有 `StageSourcesImpl` 一次校验全部当前根，并生成完整Save All预览；此阶段不记录历史、不写盘。

`StageMove` 重算全部来源字节、目标、include报告、根差异及预览代次，准确一致后才调用 `StageSources` 接受双文件变化。历史仍使用原32组/128MiB预算，来源仍受单文件8MiB/集合64MiB限制。读取和编辑的是配置XML，不参与DAQ原始接收、文件复制或硬件命令。

## 11. Save All中断后的持久恢复记录

### 11.1 保存之前，软件先保留什么

有实际改动的Save All现在会先创建独立恢复记录，保留全部已知配置来源的原始字节、改变来源的候选字节、根文件列表及每份内容的SHA-256。记录和来源标记全部写完后，才替换第一份来源。

记录位于第一个打开根文件的父目录：

```text
.getdaq-workspace-recovery/
  save-任务UUID/
    manifest.json           来源路径、原始/候选摘要、根列表
    original/0.xcfg ...      所有原始来源，按manifest顺序
    candidate/0.xcfg ...     有变化来源的候选
    writer.lock             当前保存/恢复者的互斥锁
    complete.json           完成后才发布，绑定manifest与最终方向
```

每个涉及来源旁还有 `.getdaq-workspace-save-路径摘要.json`，指向同一记录。保存全部完成并核对实际字节后发布complete并清理自有来源标记；恢复记录保留为历史，不自动删除。

没有改动的审阅不会生成记录。若所有临时来源文件不能准备，仍在替换前拒绝；如果记录准备或标记阶段失败，原始来源不被替换，已创建的记录保留供核对。出现部分提交、同步或结果写入失败时，窗口保留记录路径、已保存/剩余列表并冻结继续保存。

### 11.2 重开时为什么不能直接编辑

新工作区打开带未完成标记的根或共享来源时拒绝普通加载，并显示恢复路径。普通`XcfgDocument::Load`、原单文件编辑器的保存、结构修改及来源核对都遵守该待核对标记，不能通过另一个新窗口或普通配置CLI绕过它。完整候选的受控恢复解析与普通磁盘加载分开，仍能预览并明确恢复原记录。

记录不会自动完成候选，也不会自动回退。其他旧软件或外部编辑器仍可能修改文件；恢复时若实际内容不再等于记录中的原始或候选任一版本，就拒绝覆盖。标记是合作编辑器之间的协议，不是所有程序都必须遵守的操作系统访问控制或签名。

### 11.3 使用恢复窗口

1. 停止原保存者，保留磁盘文件和恢复目录。不要删除manifest、原始副本或来源标记来强行继续编辑。
2. 打开新的多文档工作区，点击 **Inspect interrupted save...**。如果刚刚打开来源被拒绝，窗口会尽量预填该记录路径；也可以选择包含manifest.json的具体 `save-UUID` 目录。
3. 选择 **Finish the reviewed candidate** 或 **Restore the recorded original sources**。前者将来源统一为原Save All的候选，后者统一回原始来源。改变方向会撤回旧预览。
4. 点击 **Preview recorded source states**。查看每个文件目前是original还是candidate、是否需要替换、当前与目标摘要；从来源列表逐个查看 **Current disk source** 和 **Selected recovery target** 的准确文本。
5. 核对所有文件及方向后点击 **Confirm reviewed recovery**。确认框默认取消；取消不写文件。只读模式可查看，禁止确认写入。
6. Yes后重新计算本次审阅、取得记录写者锁、准备全部需要替换的来源，再逐文件提交和同步。只有全部目标字节核对通过，才发布完成记录并移除自有待核对标记。
7. 成功后关闭旧工作区并重新打开。旧内存历史不会自动绑定到恢复结果；不要用旧Undo栈覆盖新磁盘内容。

完成记录不能再当作未完成任务重放。如果保存者仍运行、当前文件出现第三种内容、路径/记录/摘要变化、候选被修改、依赖无效或来源属于另一个待核对记录，恢复拒绝。预览后又发生变化，需要重新预览，不自动重试。

### 11.4 恢复过程再次中断

恢复同样逐文件执行。再次失败时，原记录仍在，来源仍只允许处于该记录的原始或候选版本；停止当前恢复者后重新审阅并选择方向。软件不会自动换一个新意图覆盖旧记录。

这提供可核对、可继续或回退的保存恢复流程，**不是任意外部读取者永远只能看到全旧或全新的跨文件原子事务**。[新版合作来源读取者](CONFIGURATION_SOURCE_TRANSACTIONS.md)在活动写者或未完成来源记录存在时拒绝读取；不遵守协议的其他程序仍可能看到混合版本。生产软件应使用已发布且绑定的配置工件，不能实时加载正在编辑的来源树。

### 11.5 空间、权限和平台范围

- 单份来源仍最多8MiB，已知来源集合64MiB，记录原始与候选逻辑集合合计最多128MiB；未改变来源不另存一份候选。
- 每个恢复根最多256个记录、原始/候选载荷合计最多2GiB。将超过上限时，在替换任何来源之前拒绝，并提示人工归档已完成记录。没有自动删除策略，避免丢掉唯一的恢复证据。
- 有未完成记录时不要清理它。已完成记录可在确认备份和用途后由使用者归档；不要修改记录内容后继续当作原记录使用。
- 新恢复目录仅当前用户访问，新记录文件仅当前用户读写；Windows的实际ACL继承和目录断电持久性仍需目标环境验证。
- POSIX记录文件及目录同步，来源每次提交后同步文件和父目录；Windows使用文件 `_commit`，不宣称已实现等价的目录断电持久性。
- 恢复依赖原规范来源路径仍存在；不提供移动记录到另一机器、重映射路径、恢复被外部删除文件或恶意同用户篡改防护。

归档已完成记录前，确认引用它的来源标记已经移除；完整保存会自动清理。残留标记须先核对，不能移动其仍指向的记录后直接继续编辑。

配置记录会增加磁盘占用，但与DAQ数据文件无关。它不保存`.graw`、不停止或恢复硬件、不解除ECC UNKNOWN，也不是跨主机的数据恢复协议。

此处`save-UUID`记录仍要求原规范路径存在。新的[文件路径迁移](CONFIGURATION_PATH_MIGRATION.md)使用`move-UUID`记录，明确保存新旧路径的存在状态；同一个恢复窗口按记录种类分派，不能将两个manifest互换或改名来绕过检查。

### 11.6 代码与验证原理

`XcfgSaveJournal` 负责新记录、来源标记、摘要及写者锁；`XcfgWorkspace::SaveAll` 在记录准备后才提交来源，并在第一文件以后任一异常保持需要重开。来源核对会识别未完成记录；原单文件来源检查使用同一标记规则。

`PreviewRecovery` 读取有界原始/候选副本，核对摘要及当前来源分类，以候选覆盖重建所有原根和脱离根的已知来源，验证选定组合。`ApplyRecovery` 重算准确审阅并检查完成状态、来源标记、当前字节和manifest，逐文件提交后记录最终方向。记录锁使用零年龄超时，避免仅因耗时长而认领仍活着的保存者。

真实独立进程已经在第一份来源同步后立即退出，留下新旧混合版本；另一个进程按同一记录恢复完成。该验证证明进程中断后的本机流程，不证明真实断电、磁盘设备故障或被立即退出子进程的LeakSanitizer清理。普通及插桩完整核心、生产恢复窗口及实际Windows范围见[验证记录](VALIDATION.md)的后续章节。
