# 在操作台审阅并提交接收计划切换

本页说明 GetDAQ 的 `Review receiver plan transition...` 窗口。它负责审阅、一次性提交原计划退休请求、查询原结果和导出证明。完整后端准备与逐节点启动命令见 [ECC计划切换](ECC_PLAN_TRANSITION.md)，身份文件的生成与权限见 [接班身份](ECC_SUCCESSOR_IDENTITY.md)。

这里的“退休”指原服务永久停止接受新的控制请求，把正常结束的周期及下一代目标保存为证明。它不会删除原始数据，也不会把失败周期改成正常周期。更换数据服务和启动新ECC需要在对应主机上明确执行。

当前源码已在本窗口增加部分失败的[原实例显式补齐](PARTIAL_HANDOFF_COMPLETION.md)。它使用操作台此前保存的原请求及提交前状态，不需要操作电脑访问ECC或数据主机的本地路径。旧候选包若没有补齐按钮，仍按命令行手册处理；不要重新提交整套退休来代替接续。

## 1. 先认识三个位置

同一次操作可能涉及Windows操作电脑、一台ECC主机和多台数据接收主机。不要把它们的路径混用。

| 内容 | 放在哪里 | 谁读取 |
| --- | --- | --- |
| 界面选择的 `successor.json` 副本 | 操作电脑，例如 `D:\DAQ\review\successor.json` | Qt读取小型JSON |
| 身份JSON内的 `plan_file` | ECC主机，例如 `/home/daq/next/successor.json` | 原ECC核对并锁定原文件，新ECC消费 |
| 界面选择的目标清单 | 操作电脑，例如 `D:\DAQ\review\data-plan-targets.json` | Qt审阅，编码到控制请求 |
| 每个目标中的 `plan_file` | 对应数据主机的绝对路径 | 对应原数据服务读取 |
| 导出的父回执 | 先在操作电脑保存，再复制到ECC主机 | 新ECC启动时核对 |
| 原始事件文件 | 数据主机输出目录 | 独立原生receiver及后续分析/归档工具 |

界面可在Windows运行，Linux上的文件锁由ECC服务自己处理。用户安装的套件为 `D:\Software\QT\5.14.2\mingw73_64`；这里不需要Windows能够打开Linux文件路径。

## 2. 准备两份审阅材料

先按后端手册生成各节点的新规范计划、新ECC固定配置以及接班身份。新审计根尚不存在，数据计划对应实际新工件，所有目标已核对。生成身份不会开始采集。

把生成的身份文件原样复制到操作电脑，不要在编辑器中重新保存、格式化、改变换行或改写JSON内的路径。身份摘要覆盖准确字节，界面使用与原生服务相同的规范编码校验。操作电脑上的副本可以有不同文件名，但里面的 `plan_file` 必须保持ECC主机原路径。

另一份文件是节点目标清单，格式见后端手册。它必须包含全部原节点，按 `agent_id` 升序且唯一；每个目标摘要必须与本节点生成的新计划一致并不同于旧计划。清单中的计划路径始终属于对应数据主机。

身份副本读取上限64KiB、目标清单8KiB；父控制请求仍有8KiB总上限。节点过多或路径过长导致请求超限会拒绝，不会悄悄拆批。窗口不读取服务认证令牌或raw来完成审阅。

## 3. 正常结束原采集

使用原操作台完成当前Run及正常收尾，确保没有运行中的Run，原ECC处于已知Idle或Described，所有数据节点正常Stopped、接收进程已回收并有正常封存证明。必要的Breakup、Reset仍按当前操作流程完成。

下列情形不能借此窗口切换：新鲜且没有正常采集历史的Idle、receiver异常退出、UNKNOWN、未处理故障或正在执行其他控制命令。按钮禁用时，先看主窗口阶段与切换窗口的控制状态文字；不要通过删除本地记录绕过。

## 4. 打开窗口并审阅

1. 主窗口加载绑定原ECC的配置，连接原服务并等待身份与状态核对。
2. 选择菜单栏的 `Review receiver plan transition...`。
3. 在 `Successor identity copy` 选择操作电脑上的身份副本。
4. 在 `Reviewed node targets` 选择目标清单。
5. 点击 `Load and review`。
6. 逐项核对原ECC实例、新快照、新身份SHA-256、ECC主机原计划路径及新审计根；逐行核对节点、原计划摘要、目标计划摘要和数据主机目标路径。

审阅关联当前原实例；连接到不同实例后需要重新审阅。选择文件或修改文件后，先重新加载。点击提交前窗口还会重新读取两份本地文件，拒绝审阅之后发生的字节变化；ECC随后独立核对自己的文件和全部目标。

## 5. 确认并只提交一次

点击 `Retire reviewed plans...` 会弹出确认框，默认选择Cancel。取消不会产生本地控制意图，也不会POST退休请求。

确认Yes后，工作线程先把提交前的正常封存状态保存为 `nativeRecordDir/plan-retirement-context.json`，把它的SHA-256与原请求键关联到观察日志，再保存准确请求，最后发送一次。状态与请求任何一项无法完整落盘，都不会POST。请求绑定原实例、原快照、原客户端持有期、随机操作ID、新身份摘要、新控制范围/持有期和完整节点目标。界面随即禁止重复提交；原控制按钮也保持禁用，包括原停止或恢复入口。元数据查询与断开连接仍可使用。

原ECC在受理前核对本机身份原文件：规范路径、所有者、0700父目录、0400文件、单链接、准确字节、尚不存在的新审计根及激活标记。它对该文件持共享锁，所以新ECC无法在退休尚未完成时提前取得启动独占锁。原服务不构造新ECC或连接新板端来“试启动”。

原ECC先保存所有节点意图，再逐节点最多提交一次；全部完成并持久记录后释放审阅锁。文件身份或内容发生变化会保持拒绝。对最终证明的核对继续有效，不因锁释放而放宽。

## 6. 看结果、保存回执

完成后操作台重新查询原状态及 `/v1/control-handoff`。对于新记录，回执使用准确保存的提交前状态核对原节点、会话及正常封存证明；当前实时身份仍须与原实例一致。它同时要求当前实时状态仍是原实例的已知Idle/Described、没有硬件UNKNOWN/错误/活动切换，并保留原控制与数据冻结。历史正常状态只用于核对原周期，不能覆盖当前硬件故障。它核对父请求、原实例/快照、全部原正常封存周期、各子请求键/证明摘要、新范围与持有期；通过后才显示可导出的回执。旧版本已完成且未保存前状态的记录可继续按原规则观察原回执，但不能据此补齐部分失败。

原控制与数据的 `needs_reconciliation=true` 在正常退休后表示预期的永久冻结。只有双方保持且无独立错误、UNKNOWN或活动操作时，才可作为成功退休回执的原状态；成功退休不会解除这两个标志。

核对成功的原回执先以 `plan-retirement-原操作ID.json` 保存到原配置指定的 `nativeRecordDir`，原有不同内容不会被覆盖。点击 `Export original receipt...` 另存可转移的准确回执，例如 `D:\DAQ\review\old-retirement-receipt.json`。导出使用完整写入及提交；错误结果或原实例改变后，窗口清除可导出的缓存。

保存回执不表示新服务已启动，也不表示真实硬件已经加载新参数。不要仅凭窗口文字就开始采集。

## 7. 断线、超时或操作台重开

保持原配置、原 `nativeRecordDir` 及其全部记录。重新连接同一原ECC后，操作台从保存的意图恢复冻结，只观察原操作；不会换ID重发，也不会把重新连接当成一次新的退休。

当原操作后来完成，操作台可只读核对并重新取得原回执。使用 `Inspect original receipt` 查询，不要重新提交。它要求同一个原实时实例及原完成请求，不能从旧缓存为不同实例生成新的控制许可。

若原ECC已经关闭且没有先保存完整回执，不能用冷重开、新目录或猜测子操作路径补造实时证明。本入口不支持原ECC冷服务接管。对于仍在原实例的部分失败，使用下一节的独立补齐入口；保留原目录和全部证据，先核对具体失败节点与原操作。

## 7.1 部分失败后在窗口显式补齐

以下例子中，节点A已退休，节点B在受理前因缺少原计划文件拒绝。原父操作为failed，旧ECC保持冻结。

1. 保持原ECC和原数据服务运行，不先重启。操作台保持原配置与原 `nativeRecordDir`。如果操作台已关闭，可重开操作台并连接同一个仍运行的原ECC；这不等于重启ECC。
2. 打开切换窗口。新增说明区会显示保存的原退休操作ID、原实例、原目标身份摘要与新范围/持有期；表格来自原请求与提交前状态。此时不重新加载另一套身份或目标清单。
3. 在对应数据主机上恢复节点B此前审阅的准确文件，保持原路径、字节及0400权限。界面不会代替用户访问或修改数据主机文件。不能改成另一份计划。
4. 等待原父请求被确认为failed且没有仍在观察的接续请求。满足前提后，`Complete original partial retirement...` 才可用。缺少原始前状态、原请求尚未终态、已有接续未确认、实例变化或独立故障时均不应提交。
5. 点击该按钮，核对确认框中的原父操作ID。默认Cancel，取消不产生意图或POST。选择Yes后，工作线程生成一个新的接续ID，持久保存单独意图，再提交一次 `complete-data-handoff`。新请求只引用原失败父ID，不能携带另一套目标。
6. 已受理节点只查询原子操作；只有明确未发送或明确拒绝的原请求才可能原样补交。原失败父记录不被改成成功，旧控制按钮继续禁用。
7. 回复丢失时，使用 `Observe saved completion`，或等待原意图轮询。该按钮只GET保存的接续ID，不生成新请求。不要把未取得回执解释为需要再次提交。
8. 如果这次接续也明确failed，保留该失败记录，核对并处理原因。只有已确认终态、原实例及原证据仍匹配，窗口才允许另一次明确确认；每次确认使用独立接续ID。不会自动循环重试。
9. 当全部原节点已核对完成，等待回执检查通过，再使用 `Export original receipt...`。回执仍引用原节点子操作。接着按下一节逐主机启动新服务与新ECC。

### 原始前状态缺失时怎么办

老操作台曾提交部分退休，但没有 `plan-retirement-context.json` 时，本窗口不会从失败后的状态生成该文件。原因是节点此时已可能退休，当前状态不能证明提交前的正常周期。保留原日志，使用已有准确证据评估命令行入口；没有准确证据时不支持本接续路径。不要手工新建、复制另一周期的状态或修改观察日志。

原状态文件与日志关联摘要、原请求键、文件身份及目录单写者共同核对。文件替换、改写、孤立文件或不完整意图会保持拒绝，不自动修复。它们都是低频控制证据，不包含raw载荷。

## 8. 在各主机明确执行后续启动

确认父操作全部完成并保存回执后，按 [后端手册第6、7节](ECC_PLAN_TRANSITION.md#6-逐节点更换数据服务) 操作：

1. 正常关闭原ECC，再关闭各原数据服务。
2. 每台数据主机使用其新配置及本节点原退休证明启动新的 `getdaq-supervisor`。子操作ID从父回执取得，不能把父操作ID当成节点操作ID。
3. 把导出的父回执原样复制到ECC主机。
4. 新ECC以新固定配置、原接班身份及该父回执启动。它重新查询所有新数据服务的身份和实时前驱证明。
5. 主窗口加载绑定新ECC快照和输入的操作配置，使用该配置对应的新本地记录目录，重新连接。
6. 核对新身份和Fresh数据状态，再人工Describe、Prepare、Configure、Start，形成新Run。

新配置选择会重新绑定界面，但不会解除原服务已持久保存的退休门槛。不要把旧记录目录改名当作新实例恢复方案。身份计划一旦消费就不能直接再次启动；已有激活标记不可以删除后重试。

## 9. 常见问题

| 现象 | 检查方式与处理 |
| --- | --- |
| Load失败或提示规范字节不符 | 对比从ECC主机复制的原文件，重新原样复制，保留其内部Linux路径 |
| 节点缺失、摘要不变或范围相同 | 回到离线准备，核对完整节点集合、真正的新部署及新ECC固定输入 |
| 本地文件改变后无法提交 | 重新加载并人工核对变动，原审阅不再有效 |
| POST超时、窗口保持 | 保存原意图，只查询原操作；超时不能证明服务未受理 |
| 第一节点已退休、后续失败 | 保留部分结果和原始前状态，核对原因后使用独立补齐按钮；不自动重发或回滚 |
| 正常完成但旧按钮仍禁用 | 这是预期行为，后续应启动并连接正确的新实例 |
| Inspect或导出不可用 | 先核对原实时身份、原操作是否完整完成及回执校验错误 |
| 新服务提示锁被占用 | 核对原进程是否正常退出，不删除锁文件或抢占 |
| 新ECC提示身份已消费 | 停止重复启动，保存激活标记和原证明；当前不是冷恢复入口 |

## 10. 架构与性能边界

```text
MainWindow → PlanTransitionWindow（小型元数据审阅）
     ↓ Qt信号
RunControl → NativeRunControl（工作线程、原意图日志）
     ↓ EccSystemClient：认证控制HTTP，最多一次POST
原ECC：本机身份审阅锁 → 全节点退休 → 父完成记录/回执
     ↓ 人工服务更替
新数据服务与新ECC：独立核对前驱证明 → 人工启动新采集

板端数据 → 原生receiver → 有界队列 → 磁盘
```

Qt界面、日志及HTTP只处理低频控制与有界JSON，不参与事件数据传输。新增功能未给receiver引入Qt或新第三方运行库。纯C++11协议核对同时供Qt与原生ECC使用，服务端的POSIX文件锁不进入WindowsGUI构建。

实现按项目既有 `.h/.cpp/.ui/.pro` 布局组织。主要入口为 `apps/envoy/plantransitionwindow.*`、`nativeruncontrol.*`、`eccsystemclient.*`、`eccclientstore.*`；原生审阅和请求证明位于 `apps/ecc/native/eccsuccessorplan.*`、`ecccontroljobs.cpp`，共享协议在 `common/control/eccprotocol.*`。

## 11. 验证边界

最初完整退休窗口的证据见 [VALIDATION](VALIDATION.md) 第70.56节；本次部分退休显式补齐见第70.61节：客户端63项、窗口95项，普通交付构建/新ECC代码插桩两组各两编码的实际MainWindow流程和新实例采集通过。窗口单测与本机合成板端的完整窗口联调应分别核对；Windows可编译和初始窗口通过不能替代新流程的人工操作验收。板端getHwServer/IceEirfu保留现有部署。真实硬件、独立目标平台、持续跨主机大流量、连续板卡占用移交、冷切换及已受理后执行失败节点的恢复仍需后续工作。
