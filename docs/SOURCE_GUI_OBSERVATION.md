# 在操作台查看源端状态

这里的“源端”是把 CoBo 内存中的数据送出去的进程；“接收端”是数据主机上把数据写入文件的进程。两者状态应分别查看。源端显示 `running`，并不能证明接收文件已经同步到磁盘；接收端进程仍活着，也不能证明源端没有故障。

本功能只查询少量状态信息。原始 MFM 波形继续由源进程直接发送给接收器，不经过操作台、ECC HTTP 服务或 Qt 表格。Qt 的刷新频率不是数据发送频率。

```mermaid
flowchart LR
    GUI[Qt操作台] -->|认证GET：小份状态| ECC[ECC服务]
    ECC -->|独立只读Ice：describeSource| Source[源进程]
    Source ==>|原数据连接：大量MFM| Receiver[原生接收器]
    Receiver --> Disk[数据文件和结束凭据]
```

## 1. 启用前需要什么

需要使用原生全系统 ECC 模式，以及带有 `/v1/sources` 接口的 `getdaq-ecc-server`。升级后的 ICE 源需实现 [源控制扩展](ICE_SOURCE_CONTROL.md)。传统 TCP、ZBUF、FDT 源没有这套远端查询接口，会明确显示 `legacy`，不能从其控制命令成功推断源状态。

已有 ECC 地址、凭据文件、配置摘要和 sender 到数据主机的映射必须正确。沿用 [原生 ECC 操作说明](NATIVE_ECC_COORDINATOR.md) 设置这些字段；本功能不建立新的控制权，也不自动修复旧会话。

## 2. 在界面中打开

1. 打开节点及连接配置窗口，选择全系统原生 ECC 模式。
2. 勾选 `Observe source state (read-only)`。
3. 保存配置，连接已配置的 ECC 服务。
4. 查看主窗口最后一列 `Source state`；错误原因同时显示在 `Error` 列。

对应 YAML 字段位于原有 `getdaq` 部分：

```yaml
getdaq:
  native_source_status: true
  poll_ms: 1000
  native_ecc:
    timeout_ms: 5000
    status_max_age_ms: 10000
```

这是现有配置的一个片段，不能单独作为完整启动配置。旧配置没有这个字段时默认关闭。关闭后，源状态查询停止；现有采集控制流程仍由原生 ECC 状态机处理。

`poll_ms` 是操作台尝试查询的间隔，可先使用 1000 ms；查询未完成时不会叠加第二份。`timeout_ms` 是HTTP等待上限，示例5000 ms给ECC默认2000 ms的整组源预算留出回包余量。`status_max_age_ms` 是上一份有效响应收到后的显示期限，示例10000 ms；它不是源机器上状态保持正常的保证。不要为了大流量传输把轮询改为逐帧刷新。

与 `native_receiver_status` 分别启用，可以同时查看源进程和接收进程。两项都只读。不要把观察开关与服务器端的告警停止策略混淆：勾选观察不会启用自动停止策略。

## 3. 如何理解显示

| 显示 | 含义 | 操作者下一步 |
| --- | --- | --- |
| `running` | 原绑定 ICE 源回答正在运行；身份与会话核对通过 | 同时检查接收端计数、错误和磁盘情况 |
| `connected`、`stopped` 等 | 源报告的生命周期状态 | 与当前采集阶段及接收会话对照 |
| `unknown` | 源明确报告结果不确定或异步故障 | 检查源日志、ECC 原操作和原接收会话；不能直接重发 Start |
| `… / control UNKNOWN` | 只读源状态可读取，但原控制对象仍不确定 | 保留原操作证据，执行明确的故障处理 |
| `legacy` / `Legacy source: state unavailable` | 传统源不支持此查询 | 查看其本地日志和现场设备；本软件不编造状态 |
| `unbound` / `No bound source` | 尚未形成可观察的已绑定源对象 | 按正常 Describe、Prepare、Configure 流程推进 |
| `busy` | 此次源观察未取得稳定对象，或查询已在执行 | 等待下一次轮询，不重建连接 |
| `unavailable` | 超时、失联、非法回答或无法核对 | 查看错误文字，检查原源服务及网络 |
| `Source observation missing or stale` | 还没有有效结果，或上一次结果超过本地时效上限 | 等待查询或排查连接；旧正常显示已撤下 |
| `Waiting for matching …` | 源观察与当前操作或接收 session 不一致 | 等待一致结果，核对配置；不将旧 Run 状态套到新 Run |

颜色帮助定位：已核对的源状态为绿色，明确源故障为红色，未观察/忙碌等为黄色。绿色仅表示这份观察有效，不是“整套采集健康”或“数据完整”的证明。

## 4. 查询原理与边界

操作台以已设置的轮询周期发送认证 `GET /v1/sources`。同一客户端最多保留一次待处理的源查询；服务端也只允许一次源观察，重叠请求返回 409，不积压一批慢查询。HTTP 工作在线程池执行，GUI 不在主线程等待 ICE 调用。

ECC 先短暂获取当前控制状态和源对象的共享句柄，然后释放命令锁，再逐个查询源。观察默认总预算为 2000 ms，每个来源最多 500 ms；剩余预算不足时不再发送新的远端查询。超时不是实时硬件保护承诺。

旧 Ice 的全局 `Ice.Override.Timeout` 会覆盖代理上的超时设置。因此观察使用独立只读 communicator，设置本次查询的短超时，禁止重试；它不会替换原控制代理，也不会用新连接继续控制旧对象。

跨平台协议解码器采用标准 C++11，响应最多 256 KiB。64 位计数以十进制字符串传输，避免 JSON 浮点数丢失超过 2^53 的整数。操作台核对服务实例、快照、配置和工件摘要，再按 sender ID、当前操作 ID 和 receiver session 对应行显示。

接口中的几个字段特别容易误解：

| 字段 | 表示什么 | 不能据此推断什么 |
| --- | --- | --- |
| `issued_bytes` | 源已尝试交给数据发送器的累计字节 | 不等于接收端已经收到或同步 |
| `locally_sent_bytes` | 本地发送调用成功返回的累计字节 | 单向Ice调用返回不证明接收写盘持久性 |
| `start_issued` | 本对象曾尝试启动生产 | false只适用于此对象历史，不可用于新对象猜测旧Run |
| `stop_acknowledged`、`drain_acknowledged` | 源生命周期记录停止和排尾确认 | 不能替代真实驱动及设备静止证明 |
| `source_end_acknowledged` | 源已得到显式结束调用的应答 | 不等于控制结果一定已知，也不是接收文件seal的替代 |
| `failure_stop_acknowledged` | 明确故障停止已确认 | 不清UNKNOWN，不产生正常结束 |
| `source_instance_id`、`receiver_session` | 这份回答对应的源对象及接收周期 | 不授予控制权，不允许接管替换进程 |

原始文件和接收结束证据仍按接收器及数据管理服务各自的字段核对；这些数字不会被操作台当成真实写盘速度。

界面时效由本地单调计时器测量，表示“收到这份有效响应后经过多久”；不把源机器的墙钟时间当成本机时钟。若来源实际状态在查询之后变化，下一个有效回答之前界面仍可能显示上一份观察。因此本功能不代替源侧错误检测，也不作为硬件安全联锁。

## 5. 出现故障时的处理原则

先查看 `Error`、源进程日志和 ECC 原操作记录，确认是哪一个实例、哪一次接收 session。保留运行目录和未完成记录。只读查询恢复，不能清除控制 UNKNOWN，也不能证明原控制连接仍有控制权。

原控制连接丢失时，即使源仍可被独立观察，Start/Stop的绑定验证也会拒绝并保留UNKNOWN；不会把观察连接变成新控制连接。诊断步骤、并发查询和Reset生命周期的验证方法见[控制断线与并发说明](SOURCE_OBSERVATION_CONCURRENCY.md)。

已有显式故障停止入口会通过原系统对象停止硬件生产，并对已绑定升级 ICE 源尝试一次停止及消费线程 join。它不排空、不补发 End、不关闭或正常封存接收器，也不清除 UNKNOWN。停止命令应答丢失时，不能靠再次查询到 `stopped` 就重放命令或伪造成功。

正常结束仍由源端在停止、静止验证和排空后，通过原数据连接发送 End；接收器核对字节、完整帧、写盘同步和退出，才形成结束凭据。故障停止与正常结束的差别见 [源控制](ICE_SOURCE_CONTROL.md) 和 [读出线程生命周期](SOURCE_READOUT_LIFECYCLE.md)。

## 6. 当前验证范围

本轮普通 Qt 流程模型已验证源 unknown、unavailable、错误 session、缓存过期和配置保存重载；客户端用例验证身份核对、精确大整数及不自动提交命令。实际窗口、跨进程 HTTP、新代码插桩和正常传输回归的最终结果统一记录在 [验证文档](VALIDATION.md)，未记录通过的项目不能据实现代码推断已验收。

测试仅使用本机模拟源及少量合成数据，所有测试输入与输出合计不超过用户要求的 20 GiB，测试后删除生成的 raw。现场板端停止、DMA/MMIO、Ubuntu 24、Windows Qt 5.14.2 MinGW、macOS、持续吞吐和断电恢复仍需各自验证。
