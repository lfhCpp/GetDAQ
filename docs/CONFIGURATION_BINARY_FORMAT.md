# 旧二进制配置的转换与使用

## 1. 这项功能解决什么问题

旧 CompoundConfig 可以用 `.bcfg` 保存配置。它和采集文件 `.graw` 完全不同：前者保存对象、参数值、类型、单位和范围，后者保存探测器事件。新功能用于离线读取旧配置，或生成供旧配置库读取的版本 1 文件；它不接收、转发或处理采集事件。

操作台和 `getdaq-config` 使用相同的 `XcfgBinary` 转换核心。生产程序不需要旧 CompoundConfig、Boost、Spirit 或 TinyXml。既有 Qt Core 和项目自己的范围解析器足够；窗口采用 `.h/.cpp/.ui` 结构。原生数据接收器、导出器和 catalog 工具不链接这个转换模块。

转换成功只说明配置文件可以解析，不能说明它适合当前板卡、已加载到板卡，或可以解除 ECC 的 UNKNOWN。发布配置、选择部署、执行 Configure 和现场读回继续使用各自的流程。

## 2. 在操作台导入旧文件

1. 打开配置编辑窗口，点击 **Review legacy binary configuration conversion...**。没有预先打开 XML 也可以导入。
2. **Direction** 选择 **Import binary to XML**。
3. 点击 **Choose binary input...**，选择原 `.bcfg`。不要选择 `.graw`。
4. 点击 **Choose NEW output...**，指定尚不存在的 `.xcfg` 文件。父目录必须已存在。
5. 点击 **Build preview**。程序检查二进制结构、版本、所有引用和范围，再用正式配置模型检查转换后的 XML。
6. 阅读预览及对象/参数数量。确认后点击 **Save reviewed NEW file**。
7. 保存时重新读取原文件，重建转换结果并比较此前审阅的来源字节及输出字节。原文件变化或输出名称已被使用时拒绝保存。
8. 保存后，通过配置编辑窗口原有 **Open .xcfg...** 明确打开新 XML；转换窗口不会替换当前编辑会话或自动清除其历史。

改变输入、方向、对象路径、模式或输出名称会撤销旧预览。转换和保存使用后台任务；关闭窗口不撤销已经提交的文件操作，保存后可检查所选输出路径。原二进制文件始终保留。

只读编辑模式也可以转换到新的文件，和已有 XML 导出一样；它仍不能修改原配置。

## 3. 将 XML 导出给旧软件

1. 先在配置编辑器打开并核对 XML，包括它引用的所有本地来源。
2. 打开转换窗口，将方向改为 **Export loaded XML to binary**。
3. 填写对象路径。整份配置使用根对象，例如 `Setup`；子对象使用编辑器里的路径，例如 `Setup/CoBo[0]`。
4. 选择内容模式：

| 模式 | 输出内容 |
| --- | --- |
| Declarations including defaults | 展开本地 include，保留选中对象的本地声明和默认块；不补充选中声明之外的继承值 |
| Effective concrete object | 冻结选中具体对象及其有效子对象/参数；不能选择 `[*]` 模板作为具体对象 |

5. 指定新的 `.bcfg` 文件，生成预览并阅读解码后的 XML。
6. 点击保存。程序重新检查全部来源与候选字节；保存后原 XML、include 文件和硬件不变。

导出先复用已有 XML 导出语义，再编码；编码后解码并比较有效配置摘要。发现类型、值、单位、范围或有效对象语义不一致就拒绝，不把“能够生成一些二进制字节”当作正确导出。

二进制只保存配置语义，不保存 XML 注释、处理指令、排版、字符引用写法、原 include 地址或文件分布。不要用它作为原工作区的完整备份；需要继续保留源 XML 和引用文件。

## 4. 命令行操作

使用构建生成的 `getdaq-config`，下面的名称只是示例，请改为实际路径：

```bash
getdaq-config import-binary old.bcfg new-readable.xcfg
getdaq-config export-binary setup.xcfg Setup declarations new-legacy.bcfg
getdaq-config export-binary setup.xcfg 'Setup/CoBo[0]' effective cobo0.bcfg
```

两种命令都要求输出不存在，且不会执行硬件操作。CLI 在一次调用内建立预览、重算并保存；可视化逐项审阅使用窗口。遇到失败返回非零，标准错误显示原因；已有目标不会覆盖。

如果写盘或刷新失败，保留已经独占创建的未完整输出并报告错误。该文件不能当作成功结果；先检查它再选择另一个新名称重试。此流程不提供断电持久性保证或多文件事务。

## 5. 格式和兼容边界

收到的旧库版本 1 按大端字节顺序保存：

| 顺序 | 内容 |
| --- | --- |
| 版本 | 2 字节，当前仅接受 1 |
| 字符串表 | 4 字节数量，随后为以 NUL 结束的 UTF-8 字符串 |
| 属性类表 | 4 字节数量；每类包含名称引用、类型、单位引用及范围 |
| 对象树 | 类引用、ID 字符串引用；对象包含 2 字节子项数量，标量包含相应值 |

类型编码为对象 0、int 1、hex 2、real 3、bool 4、string 5。`int` 为有符号 32 位；`hex` 的线上槽为 8 字节，但收到的旧库 `Hex` 实际是无符号 32 位；`real` 为有限 IEEE-754 双精度；`bool` 仅允许 0/1；字符串通过表引用。名称路径共享属性类，不按实例 ID 分成不同的类。

新 XML 模型可以表达 64 位整数，不意味着旧二进制可以无损表达。导出超过 signed32/unsigned32 的值或范围端点明确拒绝；导入 hex 槽高 32 位非零也拒绝，避免模仿旧解析器默默丢弃高位的行为。非有限实数、非法 UTF-8/XML 字符、未知版本/类型/范围代码、无效引用、截断或尾随内容均拒绝。

范围支持旧格式的枚举和区间，包含/不包含/无穷端点。字符串范围保留引号及转义；实数范围需要保留实数类型，整数值样式的实数端点也不会误改为 int。转换值使用明确字符引用保留首尾空格和换行，不受旧 XML 库的普通空白折叠影响。

当前限制为每份输入/输出 8MiB、字符串/类/节点最多 100000、树深小于 128、枚举最多 4096 项、每个对象最多 65535 子项；解码还有累计展开内容预算，防止小表被反复引用放大。名称使用现有模型支持的简单 XML 名称，ID 不允许路径分隔字符。命名空间、额外 XML 属性、数据库/网络来源及其他版本未实现，不应据此宣称整个旧库兼容。

## 6. 验证怎样理解

`tests/binary_configuration_integration.py` 调用新生产 CLI 和真实旧库：读取收到的 `daq.bcfg`、`daq2.bcfg`，核对全部标量，再验证新导出的二进制能够被旧库读取；另用旧 `BinaryFormat` 实际编码五种标量、范围、整数边界、默认/具体对象和字符串空白，再交给新程序导入。

测试参考库的 Boost/TinyXml 仅位于独立验证目录，不链接生产程序，也不修改 `source/`。旧 `Document::exportSubConfig` 的二进制路径没有先打开输出流，单看返回成功不能证明文件生成；参考探针沿用旧库自身二进制测试的方法，显式以 Write|Binary 打开 FileStorage，然后调用原 BinaryFormat。

核心测试另外覆盖每个截断前缀、未知版本、尾随字节、32 位溢出、非法 bool/real/表数量、确定性变异输入、旧审阅和目标覆盖拒绝；窗口测试真实点击预览和保存，核对新文件与保留的原来源。实际数字和证据目录见[验证记录](VALIDATION.md#7034-旧二进制配置转换与实际旧库对照2026-10-13)。测试只有小型配置文件；完整窗口组的其他模拟采集数据仍按 256MiB 保守预算清理。

这些是本机格式与界面验证，不证明现场固件加载、所有旧平台 ABI、物理硬件恢复或持续采集性能。
