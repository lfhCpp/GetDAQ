# 保存接班身份及一次性启动

本页记录70.52身份组件；后续已加入[原ECC服务交接、原生操作工具与两个独立进程验证](ECC_SERVICE_HANDOFF.md)，并由[计划切换流程](ECC_PLAN_TRANSITION.md)及[Qt审阅窗口](ECC_PLAN_TRANSITION_GUI.md)支持不同实验工件/接收计划的受控实例更替和新周期。本身份文件本身只固定接班者，不会切换运行中的服务或证明板端已加载新参数；真实板卡与不中断板卡主机占用移交仍待验证。

## 1. 为什么需要保存身份

[离线规划](ECC_SUCCESSOR_PLANNING.md)能够提前算出新实例的快照和数据控制范围。但普通数据适配器每次构造时都会重新生成随机持有期。如果旧实例向临时对象交接，再启动真正的服务，真正服务的持有期就不同，不能接纳原回执。

现在可以先把接班者的持有期和配置一起保存到小文件，交接时引用确定的目标，随后由真正服务一次性使用它。这是控制元数据；不接收、解析或转发原始事件数据，不改变独立原生接收器的性能路径。

本页只说明接班身份文件、离线创建/核对及启动接线。完整计划切换须按页首链接执行原ECC退休、数据节点换计划、新ECC核对和人工启动新周期；不能仅凭接班身份参数完成切换。板卡主机占用连续移交和真实硬件加载核对仍待，不能用伪造回执或删除标记绕过。

## 2. 文件分别代表什么

| 文件 | 作用 | 不能单独证明什么 |
| --- | --- | --- |
| 固定配置 `service.json` | 冻结工件、拓扑、服务及接收节点 | 当前数据控制权 |
| 接班计划 `successor.json` | 保存输入摘要、快照、范围、随机持有期及路径 | 旧实例已交接 |
| 原回执 `old-handoff.json` | 原控制者完成全部节点交接后的实例、操作及证明 | 接班时远端状态仍一致 |
| 激活标记 `successor.json.activation.json` | 绑定计划SHA、激活ID及进程号，记录已尝试使用 | 该进程仍存活或启动已成功 |

进程号仅供追溯。持有期是身份，不是密码；计划不保存认证令牌内容，服务仍使用原有认证配置。

## 3. 离线创建

先冻结接班配置，使用一个新的、尚不存在的运行审计根。不能覆盖历史快照或复用旧审计根。计划文件父目录必须预先存在、为当前用户所有、权限0700，使用规范绝对路径；目标文件尚不存在。

```bash
mkdir -m 700 /absolute/private-successor
getdaq-ecc-server --config /absolute/new/service.json \
  --create-successor-plan /absolute/private-successor/successor.json
```

程序读取固定输入，使用与真实启动相同的原生编译函数，独占创建计划、同步文件及父目录并设为0400。它不建立运行审计根、不取得板卡占用、不连接远端或启动接收器。这里只生成小型控制文件。

重复创建拒绝，不覆盖。之后不要更改配置、引用文件、审计根或移动计划；修改需要重新评审接班目标，不能沿用原回执。

## 4. 离线核对

```bash
getdaq-ecc-server --config /absolute/new/service.json \
  --check-successor-plan /absolute/private-successor/successor.json
```

核对重新计算全部绑定，要求规范序列化字节完全一致，成功输出原计划JSON。计划绑定自身绝对路径，复制或改名不能产生可使用的第二份身份；符号链接、额外硬链接、错误权限和文件身份变化拒绝。

核对成功不表示计划未使用，不表示旧实例交接、板卡释放、硬件配置加载或现场停止。已经存在激活标记的文件仍可只读核对，这不会恢复其启动资格。

| 字段 | 含义 |
| --- | --- |
| `plan_file` | 计划自身原始绝对路径 |
| `service_id` / `controller_id` | 固定服务名称与数据控制者名称 |
| `input_binding_sha256` | 固定配置与引用工件绑定 |
| `snapshot_sha256` | 与实际构造共用编译函数得到的父快照 |
| `data_lifecycle_binding_sha256` | 全部接收节点、计划和端点绑定 |
| `data_controller_scope_sha256` | 父快照与审计根派生的数据控制范围 |
| `receiver_controller_epoch` | 生成一次、供实际启动使用的随机持有期 |
| `audit_root` | 接班实例预定使用的全新审计根 |

## 5. 实际启动的接线

原控制者须向精确范围和持有期完成[数据控制权交接](DATA_CONTROL_HANDOFF.md)，保留全部节点原回执。完整交接入口接续完成后，接班服务采用以下参数形式：

```bash
getdaq-ecc-server --config /absolute/new/service.json \
  --successor-plan /absolute/private-successor/successor.json \
  --handoff-receipt /absolute/private-successor/old-handoff.json
```

1. 读取配置、认证和有界原回执，核对计划。两个启动参数必须同时提供。
2. 尝试打开控制端口；端口已占用时停止，不因此消费计划。
3. 非阻塞独占锁定计划原文件，检查审计根和激活标记均不存在。
4. 独占写入、封存并同步激活标记。后续失败也保留标记，服务生存期保留计划锁。
5. 数据适配器使用计划持有期。构造ECC之前再核对实际快照和范围，随后由原有机制取得主机占用、建立审计根；父根绑定也必须匹配计划。
6. 接纳原回执，从全部原数据实例重新查询交接操作和正常封存周期，执行新的停止检查。全部通过才完成网络作业入口构造及启动后台监视。

没有回执时，计划适配器在远端查询/命令之前拒绝。只匹配目标摘要不够，还须完整节点、原操作/证明及当前所有权一致。旧原始数据保留，不经过Qt复制。

不带这两个参数的普通启动继续使用原随机持有期及恢复门槛。不能单独提供回执，不能混用离线动作与启动动作，没有直接接受任意持有期字符串的命令行参数。

## 6. 失败如何处理

| 现象 | 原则 |
| --- | --- |
| 配置、路径、权限不匹配 | 核对原输入来源，不改文件使其勉强通过 |
| 计划锁被持有 | 不并行启动、不排队接管，先核对原进程和操作 |
| 激活标记存在 | 已尝试使用，拒绝自动冷启动或重复沿用持有期 |
| 写标记后启动失败 | 保留标记、可能建立的审计根和节点状态，不能删标记重试 |
| 旧板卡主机占用尚未释放 | 拒绝启动；连续移交尚待实现，不抢锁 |
| 无效回执、节点失联或封存不一致 | 不开放新采集，不自动回滚交接或重发旧动作 |
| 运行中计划或标记被篡改/替换 | 原对象保持故障，恢复字节不清门槛；原负向清理仍须满足既有条件 |

若失败发生在写标记之前，本对象保持激活故障，但不能据此声称完成了数据交接。写入中断可能留下不完整文件，也不自动修复/覆盖。文件与锁保证协作程序一致性，不能抵抗同账户故意删除全部历史；服务不提供这种删除入口。

## 7. 架构与依赖

`apps/ecc/native/eccsuccessorplan.h/.cpp`实现C++11原生对象，复用本地严格JSON、SHA-256、文件和随机数封装。新增核心不依赖Qt、不引入第三方库。服务外壳只处理命令行与控制HTTP；`EccControlJobs`持有计划对象，确保锁和文件检查长于数据适配器、ECC及工作线程。

计划变更进入现有外部输入故障门槛，不重新加载配置、不把旧失败采集变成正常封存。原负向收尾继续沿用原冻结目标和适用条件。

## 8. 验证范围

专用离线测试在额外拒绝并记录网络调用的环境执行，覆盖创建、复制、链接、内容/标记篡改及恢复保持、未激活/重复/消费后激活、父快照、回执门槛、实际ECC作业构造的无效回执拒绝及命令行冲突。只操作私有配置和小型审计文件，无原始载荷。

另有真实本机联调：原数据适配器正常采集封存后，向离线保存的身份交接；新的 `EccControlJobs` 从同一计划和原回执构造，重新查询两数据服务并核对原封存周期。两种编码均通过，启动没有写硬件，原载荷摘要保持；同版原普通服务完整流程两编码也通过。交接回执、计划、激活标记和新状态之间的范围/持有期/摘要均有独立断言。

本页阶段的普通/插桩结果和摘要见验证第70.52节，该阶段入口是原生作业构造。后续70.53已接续带新参数的独立ECC进程和旧服务交接，见页首链接；不同实验参数/接收计划切换、多物理主机、断电、独立平台或持续吞吐仍未验证。整体完成度不能由本子功能用例数推导。
