# 在线导出：断连回收、重连与客户端实现

本文说明 `apps/datareceiver/Exporter` 的当前行为。导出是独立分析支路；接收器以 `.graw` 保存为主输出。Qt 控制台不接收或转发这里的帧，没有新增网络库依赖。

## 1. 修复的问题

旧实现只在发送消息时发现客户端断开。如果采集暂时没有新帧，客户端已经退出，服务端仍保留它的连接记录。累积八次后会占满最大八个名额，后来的分析客户端被拒绝，必须等下一帧出现或重启才能恢复。

当前独立导出线程即使没有排队帧，也通过非阻塞 socket 检查客户端读取订阅是否结束，释放连接及其未发送消息。在接纳新连接之前先回收已经结束的名额，保持八客户端上限，不扩大队列，也不增加写盘线程或 Qt 的工作。

冻结的旧程序已经在真实本机 TCP 上复现“八个已关闭连接仍占位，第九个被拒绝”；当前普通和 ASan/UBSan/LeakSanitizer 程序分别通过修复后的同类检查。不是仅修改计数或以重启进程替代重连。

## 2. 接收端口与导出端口分别连接谁

```text
板端发送器 → --port：原始 MFM 输入 → 写盘
                                     └→ --export-port：分析客户端主动连接并读取
Qt操作台   → ECC/数据管理服务/只读状态接口
```

举例独立测试：

```sh
mkdir -p /tmp/getdaq-export/incoming
./build-receiver/getdaq-receiver \
  --output /tmp/getdaq-export/incoming \
  --port 46005 --status-port 46015 --export-port 46007 --once
```

此时分析客户端连接 `127.0.0.1:46007`，发送器连接 `127.0.0.1:46005`。启动后可能长时间没有帧，这是正常等待，不能把短暂无数据当成 TCP 结束。两个端口不能互换，分析客户端不要向输入端口发送长度消息。

旧 ECC 的 `exporter_port` 指板端第二个主动发送目标，与本程序下游 `--export-port` 是两个概念。采用接收一次再导出时，应按[数据服务手册](DATA_SERVICE.md)配置板端目标，不能因为端口编号相同就同时打开两条原始采集连接。

## 3. 客户端的线上格式和连接规则

格式保持不变：

```text
8字节 little-endian uint64帧长度 → 对应长度的原始MFM帧 → 下一消息
```

长度不包括自身八字节。一次 recv 不保证收到完整头或完整帧，客户端要按剩余字节循环读取，并限制允许的帧长度。MFM 帧自身可以是另一种字节序，不能使用长度头字节序代替帧头中的标志。

这是单向读取订阅，不接收客户端命令、确认、心跳或数据。**客户端应保持 socket 的写方向打开，不调用 `shutdown(SHUT_WR)`。** 当前实现将客户端写方向 EOF 视为结束订阅；向该端口发送任何字节也结束订阅，可能表现为正常 EOF 或内核 TCP reset。若现有分析客户端会半关闭写方向，先修改该连接用法并单独验证互通；不要宣称所有旧客户端已兼容。

需要退出时关闭整个 socket。需要继续观察时重新创建连接。重连只从之后发布的完整帧开始，不补发旧帧；服务器丢弃该连接的残留队列。已经读取了半个长度头或半个帧时遇到断线，客户端要丢弃那条未完成消息，在新连接中从新的八字节长度开始，不能拼接两个连接的数据。

服务端最多保留八个客户端。第九个可能立即收到 EOF；等某个已接纳客户端结束、名额回收后，再建立一个新连接。客户端自己限制重试频率，不用重启接收器来刷新名额。

## 4. 队列和录盘为何继续独立

每客户端仍限制配置的字节预算和 4096 条未发送消息。预算按尚未释放的完整帧副本计算，发送半条消息不提前归还。超限或 socket 错误只断开对应分析客户端，文件主路径继续接收完整帧。

导出线程检查的 socket 已设置非阻塞，没有读取输入帧或等待客户端应答。连接列表及共享消息队列保持同一互斥锁保护，断连时释放共享引用，其他客户端自己的队列保持。写盘线程仍只同步发布有界消息，原始接收块不会交给客户端长期持有。

这不是可靠双写：接收器退出时不等待所有分析队列送完，也没有下游处理确认或历史重放。客户端快、连接恢复成功或 `export_bytes` 增加都不能证明在线分析收到全部事件。文件完整性、发送端溢出和事件计数要另行核对。

## 5. 状态如何判断

在接收器运行期间查询：

```sh
curl http://127.0.0.1:46015/status
```

curl 是可选查看工具，不是程序依赖。以下字段用于观察：

| 字段 | 含义 |
| --- | --- |
| `export_clients` | 当前已接纳且尚未回收的观察连接数 |
| `export_disconnections` | 客户端结束、错误、非法输入、队列超限、名额上限拒绝的累计次数 |
| `export_bytes` | 向各客户端写入 socket 的总字节，包含八字节长度头；不代表分析程序已处理 |
| `export_failed` | 导出工作线程发生异常 |
| `received_bytes` / `frames` | 原始采集路径计数，不是导出成功计数 |

回收在导出线程的循环中进行，HTTP 字段来自多线程，不能把单次查询当成连接列表的事务快照。短暂看到刚结束的客户端仍计数是允许的；空闲时持续不回落才需要排查。

分析客户端结束不改变板端输入的 EOF、文件 seal 或采集状态。不要用 `export_clients==0` 判断可以归档，也不要因为没有分析连接就停止数据接收。

## 6. 复查、证据与清理

```sh
python3 tests/build_receiver_validation.py build-receiver
python3 tests/exporter_reconnect_integration.py \
  build-receiver/getdaq-receiver build-receiver/export-reconnect-new-check
```

专项检查：连续二十次没有原始数据的连接/退出、八连接上限和全部释放后的恢复、写方向 EOF、非法客户端输入，以及恢复后一个完整帧的导出/落盘/EOF/seal。成功组实际原始输入仅 **4096 字节**；使用自身新建目录，成功、失败和可处理的中断都会先结束进程，再删除合成 `.graw`，只保留 SHA、日志、seal 和清理清单。SIGKILL/断电/文件系统故障仍可能阻止清理；此规则不用于真实 Run。

本轮普通/插桩分别通过专项、完整核心、原 TCP 五组回归及 FDT/ZBUF 十二场景。原 TCP 回归每组约32MiB，顺序执行，sentry 是已有普通 Qt 程序，不扩大成整个软件栈插桩证明。所有生成载荷均清理，每轮全部流合计低于用户 **20GiB** 总上限。

证据日志为普通/插桩构建目录的 `results-export-reconnect-final.txt`、`results-export-core-final.txt`、`results-export-raw-regression-final.txt`、`results-export-transport-final.txt`。旧复现日志 `build-receiver/results-export-reconnect-before-final.txt`。独立归档 `build-receiver/validation-export-reconnect/`不含原始载荷或凭据；`tests/archive_exporter_reconnect_validation.py` 默认复查当前输入，`--historical-only`只核对归档。

实际环境Ubuntu20.04.6/GCC9.4、本机合成发送器与分析 socket。真实旧分析客户端、跨主机/跨字节序、网络设备、目标平台、可靠输出和持续吞吐仍待验；本次没有实现旧 ICE 数据入口。源码接口只有单向 `DataProcessor::processData`，没有采集结束方法，后续不能把它的调用完成或适配进程退出当成板端自然 EOF。
