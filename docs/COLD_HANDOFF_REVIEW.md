# ECC重启前后怎样离线核对交接证据

本页说明新增的 `getdaq-ecc-handoff review-cold`。它读取原交接的持久记录，输出一份历史审阅报告；原ECC已经停止时也能执行。它不连接板卡或数据服务，不执行冷恢复，不清除UNKNOWN，也不授予新的采集控制权。真正的冷实例接管仍需后续实现。

## 1. 为什么需要另存交接前状态

假设节点A已保存退休证明，节点B在受理前因计划文件不存在而返回412。原ECC随后关闭。新进程不能仅看当前节点状态就认定“两个请求都没发过”，也不能把当前状态当作交接前的正常采集周期。

新版本在发送任何节点请求之前保存两类证据：

| 文件或记录 | 能说明什么 |
| --- | --- |
| `intent.json` | 全部原节点请求的准确字段，包括原实例、计划、持有期和下一代目标 |
| `handoff-context.json` | 每个节点在交接前的正常Stopped状态、原PID/会话/输出目录及seal；绑定原意图摘要、范围、持有期和审计路径 |
| `remote.jsonl` 的首条intent | 上下文的SHA-256已先保存，之后才允许开始发送 |
| `before_post`／`node_explicit_submit` | 准备发送对应的原子请求；此后没有准确回复就按结果不明处理 |
| `explicit_rejection` | 该次提交明确收到409或412，绑定原操作ID、请求键及HTTP状态码 |
| 后续接续目录中的意图与日志 | 原请求后来是否再次被明确提交、拒绝或确认完成 |

这些写入会同步文件，发生在低频控制流程中。普通采集的数据热路径不增加此文件，Qt也不接收或传送原始事件。

409/412只说明那一次明确回复是拒绝。若后一次提交丢了回复，就不能继续依靠前一次412认定“从未受理”。审阅器会合并所有关联接续尝试；任何后续结果不明或受理证据都使该节点转为只应先观察原ID的类别，不因目录排序不同而改变结论。

## 2. 三个参数分别是什么

命令在原ECC主机上执行：

```bash
bin/getdaq-ecc-handoff review-cold \
  /home/daq/old/ecc-service.json \
  /home/daq/old/controller/operations/original-retirement-id/data-handoff \
  /home/daq/review/cold-review-001
```

请替换为实际路径：

1. `OLD_CONFIG`：原ECC服务启动时使用的固定JSON配置，不是Qt操作台的运行YAML。工具用它重新计算接收计划绑定、父快照和控制范围，并核对原审计根。
2. `ORIGINAL_HANDOFF_AUDIT`：原ECC主机上的原交接数据审计目录。操作ID可在保存的原父请求中找到；生产入口通常是 `原audit_root/operations/原操作ID/data-handoff`。它不是某个数据节点的子操作目录。
3. `NEW_REPORT_DIRECTORY`：一个尚不存在的新目录。其父目录必须已存在、使用规范绝对路径且没有路径别名；输出必须在原控制器根之外。工具不覆盖旧报告，也不把报告写回原证据。

原配置及其引用的硬件描述、实验工件等固定文件仍须可读、匹配。离线模式不读取或要求保留ECC及节点认证文件；配置中原有的认证路径声明仍需保留，不能为审阅而改写原配置。默认控制模式继续要求认证文件有效，离线配置对象不能启动ECC控制。此版本不提供“复制到另一条路径后仍当作原控制器”的转换：原绝对路径本身参与范围绑定。

工具不需要原ECC或节点服务在线。现场查看历史时可以先做审阅；看到报告不意味着可以立即启动新ECC或继续旧Run。

## 3. 怎样阅读review.json

成功退出后，新目录包含 `review.json`。首先检查工具是否正常返回；不要只凭文件存在判断审阅成功。

| 字段 | 含义 |
| --- | --- |
| `original_scope_sha256`／`original_epoch` | 原数据控制范围与持有期，不是本次命令新生成的控制身份 |
| `snapshot_sha256`／`binding_sha256` | 原父配置快照及接收端点/计划的绑定，不证明硬件当前已加载 |
| `original_intent_sha256` | 原节点请求集合的准确字节摘要 |
| 每个节点的实例、计划、会话、操作ID和请求键 | 用于随后人工对照原节点历史；不由审阅器改写 |
| `historical_delivery=never_submitted` | 在已提交的上下文及完整审计中没有该节点的发送标记；仍需今后的实际恢复入口核对当前原实例和会话 |
| `historical_delivery=explicit_rejection` | 保留了明确409/412，且所有后续关联尝试均没有不明或已受理结果；`http_rejection`给出状态码 |
| `historical_delivery=uncertain_or_accepted` | 已受理、已完成或投递不明；不能据此重新POST，应先查原操作ID |

下列字段在本入口中始终为false：

- `current_remote_identity_checked`：没有查询当前数据服务，不能证明它仍是原实例。
- `control_granted`：没有新控制许可。
- `hardware_unknown_cleared`：没有清除原生硬件UNKNOWN。
- `cold_recovery_executed`：没有执行冷接管。
- `raw_payload_read`：没有打开事件载荷文件。

这里的 `original_epoch` 是原数据控制持有期，不是Qt请求中的 `client_epoch`，不能互相代填。报告描述的是历史证据。已封存周期的证明与此刻硬件是否正常是两回事；后者不能从旧正常状态推断。后续真正恢复还必须核对当前服务实例、原请求历史、正常封存周期、原控制权以及独立故障，不能把本报告当作恢复凭据。

## 4. 不要混淆两份上下文

| 位置 | 文件 | 用途 |
| --- | --- | --- |
| 操作电脑的 `nativeRecordDir` | `plan-retirement-context.json` | Qt在原父退休请求前保存的整系统状态，用于[原实例窗口接续](ECC_PLAN_TRANSITION_GUI.md#71-部分失败后在窗口显式补齐) |
| 原ECC主机的原交接审计目录 | `handoff-context.json` | 后端在发送节点子请求前保存的数据周期，用于本页离线审阅 |

两者格式和绑定不同，不能互相复制、改名代用。新审阅器需要本版本开始生成的后端上下文；旧交接没有这份文件时保持拒绝，不从失败后的状态、回执或猜测PID补造。

## 5. 什么情况下会拒绝

- 原配置、父快照、根路径、接收绑定、范围、持有期或原请求不一致。
- 上下文不存在、原日志没有先承诺上下文摘要，或上下文不是正常Stopped及完整seal。
- 原日志被截断、同一尝试出现重复提交标记、拒绝记录没有先前发送标记，或500等结果被冒充成明确未受理。
- 上下文、意图、日志的字节或文件身份改变，文件不是当前用户所有的0600普通单链接文件，或目录/接续集合在审阅期间变化。
- 文件超出1MiB、相关元数据总量超出64MiB、目录条目或日志记录超出8192项预算。
- 输出目录已存在、指向原控制器根或使用非规范父路径。

拒绝后保留原证据，不删目录绕过。曾经观察到文件漂移的同一审阅对象保持故障；它不因文件后来恢复字节而自动解锁。命令本身没有修复历史或恢复硬件的动作。

## 6. 实现位置和验证范围

`apps/ecc/native/remotehandoffevidence.h/.cpp`（类名 `RemoteHandoffEvidence`）使用标准C++11与POSIX文件接口，绑定文件、解析有界JSON审计并分类历史投递。旧日志可能把带换行的规范状态对象嵌在记录内，因此按完整JSON对象解析，而不是按物理行直接切分。报告入口在 `apps/ecc/handoff/main.cpp`，后端上下文及明确拒绝记录由 `RemoteReceiverManager`保存。

相关验证入口为 `tests/run_cold_handoff_evidence_tests.py`、`tests/remote_handoff_evidence_test.cpp`，真实receiver组合及完整ECC切换继续使用既有联调程序。具体通过数量、插桩范围、交付包与raw清理记录见[验证记录](VALIDATION.md)。本页不声称真实硬件、冷接管或持续吞吐已经验收。

## 7. 开发中的冷数据补齐核心

离线审阅之后，原生层新增 `RemoteReceiverManager::CompleteColdHandoff`，用于旧管理对象销毁后补齐已经保存的**数据交接**。70.63完成原生核心，70.64由[实际冷数据补齐CLI](COLD_DATA_HANDOFF_COMPLETION.md)核对原ECC网络父记录、接班身份租约并保存回执；Qt及远程恢复任务入口尚未连接。上面的 `review-cold` 继续只读，不会调用补齐。

核心在原生ECC日志上取得独占只读锁，活ECC或其他观察者持锁时直接拒绝。它不追加 `opened`，不创建新的旧ECC实例，也不改变原状态机；历史状态必须是Idle或Described、没有未完成命令及已保存的UNKNOWN/错误。重启后的 `needsReconciliation` 仍保留，不能解释成已验证当前硬件停止。

随后重新核对原快照、交接上下文、全部后续尝试及准确原节点。新尝试在原控制器下使用一个新操作目录，先保存原请求集合再逐节点查询。已受理或投递不明的节点只查原ID；只有保留明确拒绝或从未发送的证据，且当前仍为原实例、原计划、原正常封存周期，才允许补交准确原请求。404本身不授权重发。旧失败记录、原节点请求、原控制日志及raw均不修改；失败保存独立尝试，不自动再次提交。

调用方必须在整个操作期间保持固定配置和原接班身份的检查。这个核心不会恢复任意硬件故障，不接管旧receiver进程，也不恢复已受理后执行失败的子任务。原ECC父记录、接班文件租约、明确CLI提交、回执保存及后续新实例流程已由70.64连接；70.63只代表此前原生核心的验证范围。任意硬件冷恢复和已受理后失败子任务仍不在本入口范围内。
