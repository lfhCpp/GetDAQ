# 在线导出与采集写盘的锁隔离

本功能对应70.70。原始数据仍由独立C++11接收器接收和写盘，Qt只处理配置和小型状态；没有增加第三方依赖。这里处理的是在线分析支路对写盘线程的锁影响，不改变MFM帧或旧DataExporter在线格式。

## 1. 为什么非阻塞socket仍需要改进

原来Exporter的工作线程拿着同一把互斥锁，依次检查连接、接收新连接、发送队列。每个客户端每轮最多发送1MiB、调用256次send，最多八个客户端。写盘线程保存帧后调用Publish，也要先拿这把锁才能把帧放入分析队列。

非阻塞send不等待对端接收完全部内容，但系统调用、线程调度以及一轮多客户端处理仍需时间。在这个期间，写盘线程可能因锁而等待。不能把“socket是非阻塞的”解释成“分析连接不会影响采集线程”。

## 2. 现在如何划分职责

| 执行者 | 持锁时做什么 | 锁外做什么 |
| --- | --- | --- |
| 写盘线程的Publish | 检查每客户端预算、入队或标记断开请求 | 建立一次共享帧副本；不操作分析socket |
| 导出工作线程 | 取出当前帧的共享所有权和偏移；发送后更新计数；维护连接容器 | accept、recv、send、设置socket非阻塞、close |

工作线程取得帧的共享所有权后释放锁，再发送。即使另一线程同时发布新帧，当前发送缓冲仍然有效。写盘线程不会把接收内存池的临时指针交给异步发送；分析副本和接收池块继续分开。

只有导出线程在运行期间关闭客户端socket。Publish发现某个客户端超预算时，只设置该客户端的断开请求，不再给它排入新帧。工作线程观察到请求后清队列、归零偏移并关闭连接，防止发送期间文件描述符被另一线程关闭和复用。析构先等待工作线程退出，再清理仍有的连接。

这不是无锁实现。帧副本分配/复制在发布锁外，但仍占用写盘线程的CPU和内存带宽；队列检查与更新仍需要短临界区。系统可能受CPU和内存压力影响；没有承诺硬实时延迟、任意负载零等待或生产吞吐提升倍数。

71.186进一步将每帧的长度头封装和载荷复制移出发布互斥区。副本仍只创建一次，并由最多八个客户端队列共享；若该帧本身已超过每客户端预算，则不分配副本，直接在锁内为当前观察者标记断开。客户端在复制期间退出或被工作线程回收时，随后入队阶段会自然跳过已关闭连接。该调整减少大帧复制对同一连接表锁的占用，不改变队列上限、消息格式和文件写入顺序。

## 3. 保留的兼容行为与预算

- 仍是小端uint64长度头，后接原始帧，保持x86旧DataExporter消费者兼容。
- 最多八个观察客户端，每客户端最多4096个排队消息，并服从配置的字节预算。
- 部分发送的消息仍按完整分配大小计费，不提前释放预算。
- 慢客户端断开，不让其继续累积内存，也不占住接收池块。
- 客户端写方向EOF或发送数据都结束订阅；空闲断开后可以重连。
- Publish返回只表示本次入队或拒绝已经处理，不表示分析端收到帧。接收器正常封存也不是所有在线观察客户端全部收齐的证明。

## 4. 确定性并发反例

Linux测试exporter-lock使用链接器的send包装，将导出线程明确暂停在一次发送调用内。此时另一线程发布下一帧，在发送门闩仍关闭时必须完成发布；随后释放门闩，核对两条消息的长度头、字节和顺序。测试不生成raw文件。

原实现触发“DAQ publication waited for the export socket call”，新实现通过。测试使用500毫秒等待作为卡住检测条件，这不是生产延迟指标；它证明被人为保持的发送调用不再持有发布锁。原反例、准确源码和二进制保留在build-exporter-lock/before。

2026-10-20又加入确定性工作线程故障注入：客户端已连接后，让导出线程下一次`accept`返回EIO，要求状态进入`export_failed`、客户端计数归零、断开计数加一且客户端立即读到EOF。此前工作线程的异常处理只标记失败并清零客户端数，却没有关闭已接受socket，客户端会一直留到接收器析构才断开；现在由仍唯一拥有这些socket的工作线程在失败路径逐一关闭并清空连接表。回归同时保留上述send锁反例和长度头/帧顺序检查，测试不发送原始帧或生成raw文件。

Linux入口：

```bash
python3 tests/build_receiver_validation.py build-exporter-lock/ordinary
(cd build-exporter-lock/ordinary && ctest --output-on-failure)
```

结果必须包含receiver-core和exporter-lock共两项，不能把零测试返回0当通过。GNU链接器包装仅用于Linux测试，生产程序不链接包装代码；macOS没有据此获得已运行证明。

## 5. 实际验证与数据清理

普通构建与ASan/UBSan/LeakSanitizer构建均检查上述反例、双客户端准确导出、32MiB慢客户端隔离及保存文件SHA、异常尾帧、空闲重连和十二种接收传输场景。Ubuntu24用户空间也独立编译并执行同组普通/插桩检查；系统库未整体插桩。

本轮每个系统的全部组保守预算256MiB，依次运行，合计远低于用户20GiB上限。raw只生成于自有临时目录，成功/失败的可捕获退出路径负责清理。保留程序摘要、SHA校验和清理记录，不保留合成raw。SIGKILL或断电仍需先确认原进程已停止，再按具体自有目录检查，不能扫删整个工程。

本轮故障清理变更只生成零字节合成帧；普通与ASan/UBSan/LeakSanitizer严格C++11构建的`receiver-core`及`exporter-lock`各2/2通过。精简证据位于`build-exporter-worker-failure/`，其中保存当前输入摘要、编译/程序摘要和CTest输出，不保存二进制或DAQ载荷。它验证Linux本机注入的`accept`错误与socket关闭，不涵盖所有内核/网络故障，也不是Ubuntu24候选包、macOS、真实分析客户端或持续吞吐验收。

进一步以新接收器连接原ECC和两个数据服务执行一个合成正常周期。该组合不修改原候选，记录位于build-ubuntu24-validation/rootfs/build/getdaq-exporter-lock/combination；只有result.json中passed为true才计通过。

## 6. 部署时要核对什么

本轮生产变化限定在接收器的exporter.cpp、exporter.h，以及只增加测试目标的CMake文件。新Ubuntu24候选由重新编译的接收器和上轮验证过的其余24个程序组成；逐项保留复用来源和字节摘要，不称25个程序都重新编译。inspect在新构建中另行编译，并核对与上轮字节相同。

70.74修复现已进入独立Ubuntu24候选`build-packages/getdaq-ubuntu24-20261020-ssh-exporter-failure-candidate`。接收器以严格C++11、GCC 9.4重建，其余24个程序从70.73候选逐字节复用；包内依赖由Ubuntu24 loader解析。包内接收器又通过TCP集成回归，测试脚本自动清理临时目录，最大合成raw为32 MiB。记录绑定在候选的`validation/receiver-integration-test.json`。这仍是Ubuntu24用户空间loader在Linux本机内核上的运行，不代表独立Ubuntu24机器、macOS、现场硬件或持续吞吐验收；不要只因回归通过就热替换运行中的接收器。

候选目录为build-packages/getdaq-ubuntu24-20261019-export-lock-candidate。详细回执和只读检查入口位于build-exporter-lock；正式使用前按[数据服务手册](DATA_SERVICE.md)和[操作手册](OPERATIONS.md)准备配置。

不要覆盖正在运行的receiver。先正常停止生产并确认EOF、排空与封存，再安排新进程。若固定接收计划绑定了可执行文件SHA，升级程序后需要重新生成和确认对应计划；修改二进制而继续沿用旧摘要会被正确拒绝。单独替换文件不能授权旧Run继续运行，也不解除硬件UNKNOWN。

真实板端、多源目标流量、网卡及磁盘持续吞吐仍需现场验收；项目其他缺口见[重构进度](REFACTOR_STATUS.md)。
